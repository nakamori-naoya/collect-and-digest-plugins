# 日次要約のprivacy境界

## 原則

成果物は共有される可能性があるものとして書く。原文に存在することは、成果物へ書いてよい理由にならない。判断に迷う情報は一般化するのではなく省き、必要な意味まで失う場合は要約を停止する。

## 成果物へ出さないもの

- 氏名、メールアドレス、アカウント名、顧客名、組織名など、個人や主体を特定できる情報
- token、credential、secret、cookie、認証情報、内部URL、非公開host名
- native session ID、絶対path、cwd、branch名、repository URL、未承認のrepository名・案件名
- system prompt、tool入出力、ログ、コードや会話原文の長い引用
- 契約、価格、脆弱性、未公開機能、秘密の設計判断など、公開可否を確認できない内容
- native compact summary。既存の要約であっても安全な公開用要約とはみなさない

## 残し方

- 人物や顧客ではなく、役割と行った判断を書く。
- 固有名ではなく、利用者が明示した公開可能なaliasを使う。
- secretそのものではなく「認証設定を更新した」のように作業の意味だけを書く。
- repositoryやpathではなく「対象実装」「設定」「テスト」のように変更の種類を書く。
- 原文を引用せず、達成・判断・検証・未解決事項として再構成する。

伏せ字、先頭数文字、hash化は匿名化とみなさない。元の値を推測または照合できる形を残さない。

## 保存前の確認

本文とタグを読み直し、禁止情報が無いと実際に確認した場合だけmetadataの`validation.privacy`を`passed`にする。確認できない場合は`not_checked`、混入を見つけた場合は`failed`として保存を止める。判断に必要な固有情報しかない場合も、勝手に公開可能と解釈せず停止する。
